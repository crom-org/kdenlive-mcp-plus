# Riscos e bugs

Ver também: [arquitetura](02-arquitetura.md) · [ferramentas](04-ferramentas.md) · [concorrentes](03-concorrentes.md) · [decisões](decisoes.md)

## Bugs do projeto original (`kdenlive-mcp-server`, referência de design — D-010)

- **Preset de render causa segmentation fault.** `preset=h264_hq` era passado direto como argumento ao avformat. O libx264 rejeita "h264_hq" como nome de preset de codificação ("invalid preset 'h264_hq'"), o `melt` termina com segmentation fault (código 139), e o MP4 resultante fica sem `moov atom` (ffprobe: "moov atom not found"). Este projeto evita isso pela raiz (D-005): nenhuma ferramenta jamais envia o *nome* de um preset ao avformat — só codec, bitrate e extensão já resolvidos. Testado explicitamente em `tests/presets.rs` (ver [06-testes.md](06-testes.md)).
- **`render_queue_stop` só marca o estado como parado**, sem encerrar o processo de render de verdade. Neste projeto, quando `render_cancel` for implementado (Fase 1), ele precisa encerrar o processo filho de fato — a infraestrutura para isso já existe: `engine::worker::render_isolated` usa `kill_on_drop(true)`, então basta cancelar/soltar o `Child` para matá-lo.
- **`project_open` só aceita `.kdenlive-cli.json`**, um formato próprio, não o `.kdenlive` nativo. Neste projeto, `project_open` (Fase 1) vai abrir o `.kdenlive`/XML nativo diretamente (D-004).
- **Testes insuficientes**: o original tem só 3 funções de teste, todas de sucesso básico, nenhuma com verificação real de arquivo renderizado. Este projeto tem 12 testes de integração cobrindo presets, render real (com verificação de codec/resolução via ffprobe) e o contrato completo do protocolo MCP (ver [06-testes.md](06-testes.md)).
- **`export_render` não aplica os presets.** Neste projeto, a ferramenta equivalente (`render_project` nesta fase; será renomeada para `export_render` na Fase 1, ver [05-roadmap.md](05-roadmap.md)) sempre aplica o preset escolhido.

## Divergências de documentação encontradas no projeto original

- O README do original fala em 36 ferramentas; o código do pacote PyPI 0.1.3 tem 73. O README *atual* do repositório GitHub (consultado em 22/10/2026) declara **75** ferramentas, mas as próprias tabelas do README somam só **38** — uma terceira contagem diferente. Ver [03-concorrentes.md](03-concorrentes.md) para a citação completa.
- A página do PyPI lista `cli-anything-kdenlive` como vindo do GitHub, mas o pacote 0.1.3 local traz o código em `vendor/`. Não ficou claro, na pesquisa desta execução, se esse vendor é uma cópia de código ou uma referência via `uv.sources`.
- Conflito de licença: o `LICENSE` do original diz que seu `vendor/cli_anything` é MIT, vindo do repositório `HKUDS/CLI-Anything` — mas esse repositório é Apache-2.0 (confirmado nesta execução, ver [08-licencas.md](08-licencas.md)). Esse conflito é do projeto original; este projeto não copia código de nenhum dos dois (D-010).
- A versão 1.0.0 do original, citada por uma página do Glama, supostamente gera XML que o Kdenlive pode rejeitar. Não verificado nesta execução — fica **a verificar**.

## Riscos técnicos

- **Metadados que o Kdenlive pode exigir.** Este projeto ainda não escreve nenhum `.kdenlive` do zero (só lê e renderiza um já existente). O Kdenlive de verdade costuma adicionar metadados próprios (versão do app, UUIDs de clipe, estado de UI) a um projeto salvo por ele. Não se sabe ainda, sem o teste manual de abertura (pendente, ver [06-testes.md](06-testes.md)), se um XML MLT "puro" (sem esses metadados) abre sem aviso no Kdenlive atual, ou se a Fase 1 vai precisar adicioná-los. **A verificar** na Fase 1, com o teste manual.
- **Thread safety do libmlt.** O libmlt tem estado global (`mlt_factory_init` só pode ser chamado uma vez por processo). `engine::render` usa um `std::sync::Once` para a inicialização e um `std::sync::Mutex` estático para serializar chamadas a `render()` dentro do mesmo processo — importante nos testes, que podem chamar `render()` várias vezes no mesmo binário de teste, inclusive em paralelo. Fora dos testes, cada chamada de `render_project` roda em um processo filho novo (D-003), então esse Mutex normalmente nunca disputa com ninguém em produção.
- **Avisos conhecidos do MLT/FFmpeg (não são erros fatais).** Com o fixture de teste, o MLT imprime no stderr `"No LADSPA plugins were found! Check your LADSPA_PATH environment variable."` — inofensivo, o render sai correto mesmo assim. O FFmpeg avisa `"Timestamps are unset in a packet for stream 1. This is deprecated and will stop working in the future."` e `"Encoder did not produce proper pts, making some up."` no áudio — também não impede o render, mas pode indicar que a duração exata do arquivo final tem uma pequena imprecisão (no projeto de referência do briefing original, um MP4 de teste saiu com 2,005s em vez de 2,000s; não medido de novo nesta execução, mas o mesmo aviso apareceu). Nenhum desses avisos é escondido nem tratado como erro fatal.
- **`libclang`/bindgen.** O `bindgen` precisa de `libclang.so` em tempo de build. Neste ambiente, ela não estava presente antes da instalação manual (ver [07-ambiente.md](07-ambiente.md) e decisão D-012); em outro ambiente sem `libclang-dev`/`clang` instalado, `cargo build` falha na etapa de `build.rs` com uma mensagem clara do próprio bindgen.
- **Testes de GUI.** Correção de uma suposição anterior desta execução: este ambiente **tem** um `DISPLAY` X11 real (não só Xvfb) — é o desktop de verdade do responsável pelo projeto, não um sandbox headless. O teste manual de abertura no Kdenlive foi executado de verdade (ver D-038 em [decisoes.md](decisoes.md) e a seção "Descobertas da Fase 3" abaixo), não ficou pendente por falta de tela. O risco em si se confirmou: um XML que o libmlt lê e renderiza perfeitamente pode ainda assim ser mal interpretado pela interface do Kdenlive, que impõe convenções próprias além do que o `mlt_producer_xml` exige para renderizar.
- **Revisão do protocolo MCP.** O servidor negocia com o cliente a revisão mais recente que o `rmcp` 3.6.0 suporta (confirmado: `2026-07-28`, ver [decisoes.md](decisoes.md) D-013). Revisões futuras do protocolo podem mudar campos obrigatórios do handshake `initialize`; isso é responsabilidade do SDK oficial (`rmcp`), mas vale reconferir a cada atualização de versão da dependência.
- **Coincidência de nome no preset `gif`.** O preset `gif` tem `vcodec=gif` — o nome do preset e o nome do codec do ffmpeg são, por coincidência, a mesma string. Isso é testado e documentado explicitamente em `tests/presets.rs` para não ser confundido com o bug do preset do original (ver acima e [06-testes.md](06-testes.md)).

## Riscos e descobertas da Fase 2

- **SIGSEGV sob carga concorrente pesada, confirmado na prática.** Ao rodar a bateria de testes inteira em paralelo (`cargo test`, paralelismo padrão) numa máquina com pouca memória livre e muitos outros processos rodando, o motor libmlt/FFmpeg pode travar com sinal 11 (SIGSEGV) por falta de recursos — reproduzido de verdade durante o desenvolvimento da Fase 2. Isso é absorvido pelo isolamento em processo (D-003, ver [decisoes.md](decisoes.md)): o teste/servidor continua funcionando normalmente depois — é exatamente o cenário para o qual o isolamento foi desenhado. Não é um bug de código, é contenção de recursos do sistema; recomenda-se `cargo test -- --test-threads=1` em máquinas carregadas ou com pouca memória livre, para evitar essa flakiness nos testes.
- **Causa raiz encontrada depois (D-046): o SIGSEGV era na *saída* do processo de render.** O `mlt_factory_init` registra um `atexit` (`mlt_factory_close`) que faz `dlclose` dos módulos do MLT; se uma thread de render ainda estiver dentro de um deles, o processo morre depois de ter terminado o trabalho. Confirmado com o gdb (`exit` → `mlt_factory_close` → `dlclose` com outra thread em `QPainter`, do módulo Qt do MLT). Acontecia em ~65% dos `preview_frame` de projetos verticais (1080x1920) e, mais raramente, em outros — o que se atribuía a "contenção de recursos" era, ao menos em parte, esta corrida. Corrigido: os subprocessos `render` e `frame` terminam com `_exit` (`engine::encerrar_sem_limpeza`) logo após o arquivo estar gravado — 0 falhas em 60 execuções do caso que falhava 65%. A orientação de `--test-threads=1` em máquinas carregadas continua válida para economizar memória.
- **Gap de concorrência real, encontrado e corrigido nesta própria execução.** `export_render(wait=false)` (Fase 1) não respeitava o `render_lock` compartilhado, permitindo dois renders rodarem ao mesmo tempo — o tipo exato de disputa de recursos que pode causar o SIGSEGV do item acima. Corrigido (decisão D-035) antes de construir a fila de render (Fase 2, grupo 6).
- **Convenções próprias não confirmadas contra o Kdenlive real.** Guias/marcadores (JSON numa propriedade do tractor), cor/nota de clipe da bin, e o uso do produtor `pango` em vez do formato interno `kdenlivetitle` para títulos — todas decisões documentadas (D-025, D-026, D-032), mas que podem fazer um projeto gerado por este servidor parecer "vazio" ou diferente do esperado nesses aspectos específicos quando aberto no Kdenlive real (o libmlt em si lê/renderiza tudo sem problema; é a interface do Kdenlive que pode não reconhecer essas convenções como seus próprios conceitos de guia/marcador/pasta/cor). O teste manual de abertura no Kdenlive (ainda pendente, sem tela neste ambiente) é onde isso seria descoberto na prática.
- **`clip_set_speed` com produtores sintéticos.** Funciona de ponta a ponta com mídia real (produtores `avformat`), mas um teste manual com um produtor `color`/`tone` sintético mostrou o aviso `"failed to load producer"` do libmlt, porque o produtor `timewarp` resolve seu `resource` como um caminho de arquivo, não reconhecendo prefixos como `color:`/`tone:`. Não afeta o uso real (a ferramenta `bin_import_clip` só cria produtores `avformat`, nunca sintéticos), mas é uma limitação a documentar.

## Descobertas da Fase 3 (investigação de viabilidade + teste manual real)

- **Kdenlive não tem nenhuma API D-Bus própria hoje.** Confirmado lendo `src/main.cpp` do próprio Kdenlive: ele usa `KDBusService` (modo padrão de instância única), mas nunca conecta o sinal de ativação a nada — uma segunda invocação com um arquivo não abre esse arquivo na instância já aberta, só foca a janela. Nenhuma classe do Kdenlive expõe slots `Q_SCRIPTABLE`/`QDBusConnection::registerObject`. Qualquer controle remoto real (painéis extras ou D-Bus) exige patch no C++ do Kdenlive — não há atalho gratuito.
- **O Kdenlive do `apt` (23.08.5) usa KF5**, confirmado com `apt-cache depends kdenlive` (todas as dependências são `libkf5*`), o que bate com os 441 pacotes KF5 já disponíveis neste ambiente (contra zero pacotes KF6) — um fork dessa versão específica seria tecnicamente viável aqui sem precisar compilar KF6 do zero.
- **Teste manual de abertura real, executado várias vezes (D-038/D-039 em [decisoes.md](decisoes.md)): achado mais importante da Fase 3, com resultado parcial.** Um projeto gerado pela camada de modelo (`cargo run --example gerar_projeto_exemplo_kdenlive`) foi aberto repetidas vezes no Kdenlive real (23.08.5 via apt, e também 26.04.1 — a versão que o responsável pelo projeto já tinha instalada e usa normalmente). Corrigido e confirmado: (1) a propriedade `kdenlive:docproperties.version` faltante, que causava um diálogo de erro extra (D-037); (2) a representação de trilha — cada trilha agora é um `<tractor>` envolvendo duas `<playlist>` (D-039), confirmado lendo projetos reais do próprio responsável pelo projeto (`~/.local/share/kdenlive/.backup/`) — a trilha passou a ser reconhecida pelo nome certo ("V1"/"V2"), antes aparecia como um placeholder genérico não resolvido ("V0"). **Não corrigido, apesar de duas tentativas**: os clipes da timeline (vídeo e título) continuam sendo removidos ao abrir — com um projeto de 3 trilhas + 1 transição, o Kdenlive passou a mostrar primeiro "Projeto corrompido: clipe não encontrado nos arquivos do projeto" antes de remover os clipes do mesmo jeito (pior experiência visual, mesmo resultado final). Uma hipótese testada à mão para a causa raiz (produtor duplicado por posicionamento + `kdenlive:control_uuid` compartilhado, replicando o padrão exato visto num projeto real) também não resolveu, então não foi implementada em Rust. Um problema novo foi descoberto no mesmo teste: os índices `a_track`/`b_track` da transição provavelmente também precisam de ajuste ("Composição inválida transition0 encontrada na trilha 1 em 0").
- **Resolvido em seguida (D-040):** a causa raiz era a `main_bin` sem `xml_retain=1` (bin carregada vazia pelo Kdenlive), somada a ids não numéricos, falta de `kdenlive:control_uuid`, falta da black track e títulos `pango`. Com o formato completo do Kdenlive 23.08+, o projeto gerado abre limpo no Kdenlive 26.04.1 e 23.08.5. Testes de GUI agora rodam num Xvfb próprio, com configuração isolada, sem tocar na tela nem nas configurações do usuário. Efeito colateral a acompanhar: o render ficou mais lento porque agora há composição `qtblend` de verdade entre as trilhas (como o Kdenlive faz).
- **O que isso NÃO afeta:** renderização continua 100% funcional (`melt`/libmlt leem e renderizam o XML gerado perfeitamente, confirmado de novo nesta investigação, inclusive depois da reestruturação de trilha). O problema é só de compatibilidade de ida e volta pela **interface gráfica** do Kdenlive — e mesmo esse problema melhorou parcialmente (trilha reconhecida), só não foi resolvido por completo (clipe ainda some).
- **Atualização sobre a API D-Bus (D-042):** o primeiro item acima (sem API D-Bus *própria*) continua verdadeiro, mas o Kdenlive exporta **todas as suas `QAction`** pelo D-Bus da sessão (`/kdenlive/MainWindow_1/actions/<nome>`), incluindo `file_revert`. É isso que o recarregamento automático usa, sem patch.
- **Projeto sem nenhuma trilha derruba o Kdenlive 26.04.1** (D-044): o processo some logo depois de `[BUG] "activeTrack" property is -1 but track count is only 0`. Por isso `project_new` cria V1 e A1 e `project_validate` avisa. Não foi investigado se o 23.08.5 também cai (a investigação foi feita só no 26.04.1).
- **Recarregar enquanto o Kdenlive está carregando outro projeto o trava** (observado num teste ao disparar o Revert durante a abertura inicial: a janela ficou em "Building sequences…" e depois o processo morreu). O servidor reduz o risco (só recarrega quando o Kdenlive responde ao D-Bus, nunca sobrepõe dois recarregamentos e tenta de novo se estiver ocupado), mas não consegue distinguir um Kdenlive que responde ao D-Bus no meio de um carregamento. Orientação ao usuário no README: não abrir/fechar projetos no Kdenlive enquanto o Claude edita.
- **O recarregamento automático depende do `busctl` e do D-Bus da sessão do usuário.** Fora de Linux/systemd (macOS, Windows) ele não funciona e o fluxo é File ▸ Revert à mão. Se o servidor for iniciado sem `DBUS_SESSION_BUS_ADDRESS` e sem `XDG_RUNTIME_DIR`, o `busctl` falha e o servidor registra o motivo uma vez no stderr.
- **`windowModified` só enxerga alterações não salvas do projeto atual**; um Kdenlive com dois projetos em abas/sequências usa o mesmo estado do documento. Se o título de dois Kdenlive abertos tiver o mesmo nome de arquivo (pastas diferentes), o servidor aciona o primeiro que encontrar — só recarrega um arquivo sem alterações, então o pior caso é recarregar um projeto idêntico ao do disco.
