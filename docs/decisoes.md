# Decisões de projeto

Ver também: [visão](01-visao.md) · [arquitetura](02-arquitetura.md) · [ambiente](07-ambiente.md) · [licenças](08-licencas.md) · [riscos e bugs](09-riscos-e-bugs.md)

Formato: `ID | decisão | motivo | alternativas avaliadas`. D-001 a D-010 vieram já tomadas no briefing desta execução e não foram reabertas. D-011 em diante foram tomadas durante a execução da Fase 0.

| ID | Decisão | Motivo | Alternativas avaliadas |
|---|---|---|---|
| D-001 | Linguagem: **Rust**, edition 2024 | Memória segura sem coletor de lixo; chamada direta à API C do libmlt; SDK MCP oficial (Tier 1); binário único | C (sem SDK MCP oficial, memória manual); C++ (sem SDK MCP oficial; reservado para a Fase 3); Python (mais rápido de escrever, erros só aparecem em execução); Go (usável via cgo, caminho menos natural para lib C) |
| D-002 | Motor: **libmlt 7.22.0** via FFI (bindgen + pkg-config `mlt-framework-7`) | É o motor do Kdenlive; renderização headless verificada | Chamar o `melt` por linha de comando (é o que o original faz) |
| D-003 | Render em **processo separado**: o próprio binário, subcomando `render` | Crash do motor C não derruba o servidor MCP; permite timeout e cancelamento real | Render na thread do servidor |
| D-004 | Formato do projeto: **MLT XML (`.kdenlive`)**, sem JSON intermediário | O que o agente edita é exatamente o que o Kdenlive abre | Modelo JSON próprio com conversão (é o que o original faz) |
| D-005 | Presets de render **mapeados para codec, bitrate e extensão explícitos** (Apêndice A) | O original passa o nome do preset ao avformat e causa segfault | Usar o parâmetro `preset=` do avformat |
| D-006 | **Sem fork do Kdenlive** nesta fase. Painéis extras ficam para a Fase 3 | Custo alto; o motor precisa estar estável antes | Fork em C++/Qt já; controle via D-Bus |
| D-007 | **Escopo total**: as 73 ferramentas herdadas e as novas propostas são prioridade, entregues em fases | Pedido do responsável pelo projeto | Começar só pelo mínimo |
| D-008 | Nome **provisório**: `kdenlive-mcp-plus` | "Kdenlive" é marca da KDE e.V. (ver [08-licencas.md](08-licencas.md)) | — |
| D-009 | Licença do novo projeto **pendente**. O campo `license` não foi preenchido no `Cargo.toml` | Decisão do responsável pelo projeto | — |
| D-010 | Não copiar código do `kdenlive-mcp-server`. Ele é referência de design | Evita obrigações de atribuição e mistura de código | — |
| D-011 | Projeto criado em `kdenlive-mcp-plus/` dentro do diretório de trabalho atual; as pastas de referência `original/`, `project/`, `engine/` citadas no briefing (em `/root/kdenlive-mcp-plus/`) não existem neste ambiente (acesso negado por permissão) | O diretório de trabalho estava vazio; as pastas de referência eram opcionais segundo o próprio briefing | Pedir acesso root — desnecessário, o briefing já previa essa ausência e disse para seguir sem elas |
| D-012 | O ambiente desta execução não tinha `libmlt-dev`, `melt`, `clang`/`libclang` instalados, e o `sudo` deste shell exige senha interativa que o agente não tem. O responsável pelo projeto rodou manualmente `sudo apt-get install --no-install-recommends libmlt-dev melt libclang-dev clang`, a pedido do agente | Instalar localmente sem root (via `apt-get download` + extração em prefixo do projeto) traria ~82 pacotes (GDAL, OpenCV, Qt5, LLVM — dependências do próprio pacote `libmlt7` do Ubuntu) para dentro do projeto, com risco real de problemas de ABI/rpath, por um ganho duvidoso | Instalação local sem root via `apt-get download` (mais frágil, descartada); pedir a senha de sudo ao agente (proibido pelas regras de segurança da sessão) |
| D-013 | `rmcp` fixado em **3.6.0** (a mais recente no crates.io em 22/10/2026), licença Apache-2.0. Confirmado que a revisão mais recente do protocolo MCP é **2026-07-28** (não era uma data hipotética do briefing) | É o único SDK Rust oficial (Tier 1) listado para MCP; a resolução automática do `cargo add` já trouxe a versão mais recente | — (não há alternativa real de SDK Rust oficial) |
| D-014 | `RenderOptions` ganhou os campos `extension`, `disable_audio` e `disable_video`, além dos `vcodec`/`acodec`/`vbitrate`/`abitrate`/`overwrite` previstos no briefing original | Necessários para validar a extensão do arquivo de saída contra o preset (exigido na descrição da ferramenta `render_project`) e para os presets `gif`/`audio_only`, que desligam uma trilha via as propriedades `an=1`/`vn=1` do consumidor avformat (nomes confirmados com `melt -query "consumer=avformat"`, nunca assumidos) | Deixar a checagem de extensão e o `an`/`vn` fora de `RenderOptions`, espalhando essa lógica por outros módulos |
| D-015 | `EngineError::Timeout` é levantado só pelo supervisor de processo em `engine::worker` (quando o processo filho de render excede o tempo configurado), nunca pelo laço `while mlt_consumer_is_stopped(...)` dentro de `engine::render`, que espera indefinidamente | A sequência verificada de render não descreve timeout nesse laço; timeout é responsabilidade do isolamento em processo (D-003), que já tem como matar o processo filho (`kill_on_drop`) | Timeout duplicado também dentro do laço de `render()` (dois relógios divergentes, sem benefício real, já que o processo inteiro seria o alvo de qualquer cancelamento) |
| D-016 | A fila de "um render por vez" (exigida para esta fase) foi implementada com um `tokio::sync::Mutex<()>` dentro do próprio `KdenliveMcpServer`, guardando a chamada a `worker::render_isolated` | É a forma mais simples de serializar chamadas concorrentes da ferramenta `render_project` sem construir um sistema de fila externo nesta fase | Fila com canal e tarefa dedicada (fica para a Fase 1, junto dos `render_queue_*` herdados) |
| D-017 | Sucesso e erro de `render_project` sempre voltam como `Json<RenderProjectOutput>`, com campo `ok: bool` e `erro: Option<String>` — nunca como erro de protocolo MCP (`Err(ErrorData)`, que apareceria como `isError`/erro JSON-RPC) | Atende literalmente a exigência "sucesso e erro com a mesma estrutura, para o agente tratar os dois do mesmo jeito"; um erro de protocolo obrigaria o agente a tratar dois formatos de resposta diferentes | Retornar `Result<Json<T>, ErrorData>` e deixar erros de validação de entrada (ex. preset desconhecido) como erro de protocolo — mais idiomático no rmcp, mas quebra a exigência do briefing |
| D-018 | `get_info()` do `ServerHandler` foi escrito à mão, em vez de usar `#[tool_handler(instructions = "...")]` sem `name`/`version` explícitos | Bug/pegadinha descoberta na prática, numa sessão MCP manual: sem `name`/`version` explícitos, o atalho `Implementation::from_build_env()` do rmcp 3.6.0 expande `env!("CARGO_PKG_NAME")`/`env!("CARGO_PKG_VERSION")` dentro do próprio crate `rmcp` (porque a função está definida lá), devolvendo `"rmcp"`/`"3.6.0"` como nome/versão do servidor em vez de `"kdenlive-mcp-plus"`/`"0.1.0"`. Chamando `env!()` diretamente dentro do nosso `get_info()`, ele expande no nosso próprio crate e lê o nosso `Cargo.toml` corretamente | Passar `name`/`version` como literais de string no atributo `#[tool_handler(...)]` (funcionaria, mas duplicaria manualmente a string de versão fora do `Cargo.toml`, podendo divergir dele) |
| D-019 | Logs deste processo vão para stderr via `eprintln!` simples, sem a crate `tracing`, nesta fase | Só duas ferramentas implementadas, sem necessidade real de níveis de log estruturado, spans ou filtros ainda | Adicionar `tracing` + `tracing-subscriber` desde já — complexidade sem uso real nesta fase; reavaliar quando houver mais ferramentas/eventos a logar (Fase 1+) |
| D-020 | O fixture de teste `tests/fixtures/smoke.xml` foi gerado com produtores sintéticos do próprio libmlt (`color` para a trilha de vídeo, `tone` para a trilha de áudio, via `melt -audio-track`), sem nenhuma mídia externa | Garante um teste 100% reproduzível, sem arquivo binário de mídia no repositório nem dependência de rede/mídia de terceiros | Baixar um clipe de exemplo de domínio público (mais parecido com uso real, mas adiciona binário ao repositório e uma dependência externa aos testes) |
| D-021 | As propriedades `an` (desliga áudio) e `vn` (desliga vídeo) do consumidor avformat, usadas pelos presets `gif` e `audio_only`, foram confirmadas empiricamente com `melt -query "consumer=avformat"` e testadas de ponta a ponta (gerando um GIF mudo e um WAV) antes de serem escritas em `preset.rs` | Regra explícita do briefing (verificar a API do MLT, "não assuma") | — |

Reproduzível com `cargo run --example gerar_projeto_exemplo_kdenlive` + abrir o `.kdenlive` gerado no Kdenlive real | Tentar um patch rápido e não verificado na estrutura de trilha (rejeitada: alto risco de piorar sem confirmação completa do formato; melhor registrar a pendência com evidência real do que arriscar uma mudança ampla sem certeza) |
| D-039 | **Trilha reestruturada para `<tractor>` envolvendo duas `<playlist>`** (em vez de uma `<playlist>` solta referenciada direto pelo tractor principal), com o tipo/nome/trava da trilha guardados como propriedade no próprio tractor da trilha (não mais na playlist). Implementar algo não confirmado arriscaria piorar a experiência (como aconteceu com o diálogo "corrompido" sendo pior que o "removido" direto) sem garantia de resolver | (1) Reverter a reestruturação de trilha: rejeitada — o reconhecimento correto da trilha é uma melhoria real e confirmada, mesmo sem resolver o problema do clipe. | D-040 | **Formato do documento = o que o Kdenlive 23.08+ grava; bug dos clipes sumindo resolvido.** Causa raiz encontrada lendo o código-fonte das versões 23.08.5 e 26.04.1 (`meltBuilder.cpp`, `projectitemmodel.cpp`) e confirmada abrindo os projetos de verdade nas duas versões (em Xvfb isolado, sem mexer na tela nem na configuração do usuário): a `main_bin` não tinha `xml_retain=1`, então o MLT não a "retinha" e o Kdenlive abria com a **bin vazia** — todo clipe da timeline ficava "sem referência à bin" e era removido. Ids de trilha passaram a ser `trackN` | Validado: o projeto gerado pelo Rust (`cargo run --example gerar_projeto_exemplo_kdenlive`) abre sem nenhum diálogo de erro no Kdenlive 26.04.1 (AppImage que o responsável pelo projeto usa) com bin, pastas, clipe, título, efeito e composição "Luma" visíveis na timeline; o XML de referência equivalente também abre limpo no 23.08.5 (sem nem marcar o projeto como modificado). Renderização via `melt` continua funcionando (confirmado quadro a quadro) | Reproduzir só parte do formato (rejeitada: cada parte faltante tinha um sintoma diferente — bin vazia, trilha "V0", composição inválida, título INVALID); duplicar produtor por posição na timeline como o Kdenlive grava (desnecessário: produtor compartilhado entre bin e timeline é aceito nas duas versões, confirmado) |
